# 服务器数据库与应用部署步骤

先审阅再执行。以下Linux/Bash命令从审核合入后的完整新代码根目录执行，按A→B→C→D逐段审阅，在同一个Bash会话执行。首段开启失败即停；任一步失败后不能重开会话直接跳到下一段。Windows服务器可将变量替换为带引号的真实绝对路径，调用相同Node脚本，但每条原生命令后必须检查`if ($LASTEXITCODE -ne 0) { throw '停止部署：上一条命令失败' }`，仅设置`$ErrorActionPreference='Stop'`不足以拦截Node失败。示例路径都必须修改，不推测服务器目录、服务名、端口或数据库文件名。

本交接包只提供资料和只读预检；真正迁移使用完整新代码已有工具。不启动本地teaching/init/seed，不把本机数据库覆盖服务器。已安装的新代码依赖须与其锁文件匹配，尤其better-sqlite3应在服务器对应Node/平台安装，不能复制Windows的node_modules到Linux。

## A. 核对版本与停写

1. 记录原服务提交、迁移完整清单、Node、数据库与UPLOAD_PATH/FEEDBACK_UPLOAD_PATH、静态目录和磁盘空间；核对目标是正式库。准备经审核的新代码及依赖，但先不启动新后端。
2. 停止所有写入入口、旧后端/worker、多实例及相关自动任务，安排维护窗口。`--maintenance-confirmed`不会替你停服务。
3. 另行私有保存`.env`、JWT/AI加密密钥、反向代理和进程配置；不要放进备份工具管理的manifest目录，否则验证会认为多出未登记文件。不把配置发进Git/PR或公开日志。

```bash
set -euo pipefail
APP=/absolute/path/to/reviewed-new-release
KIT=/absolute/path/to/this-handoff-kit
DB=/absolute/path/to/existing.db
UPLOADS=/absolute/path/to/uploads
FEEDBACK=/absolute/path/to/private-feedback
BEFORE=/private/new-backup-before-release
REHEARSAL=/private/new-isolated-rehearsal
REHEARSAL_BACKUP=/private/new-rehearsal-backup
APPLY_BACKUP=/private/new-backup-before-apply
REPORTS=/private/release-reports
mkdir -p "$REPORTS"
cd "$APP"

# 只读；报告文件必须不存在。老编号/缺前置必须人工核对。
node "$KIT/scripts/preflight.cjs" --app-root "$APP" --db "$DB" \
  --output "$REPORTS/before.json"
```

预检只打开明确目标，不加载新应用配置或启动服务。若没有schema_migrations、存在未知版本/迁移身份冲突、完整性/外键错误，应先停止；古老库/已知编号桥接需要单独演练，不通过手工删改记录跳过。报告可能返回阻止项且退出非零，不能忽略。

## B. 联合备份与恢复副本

```bash
node scripts/lesson-maintenance/backup-only.cjs \
  --db "$DB" --uploads "$UPLOADS" --feedback "$FEEDBACK" \
  --to "$BEFORE" --maintenance-confirmed
node scripts/lesson-maintenance/verify-backup.cjs --from "$BEFORE"
node scripts/lesson-maintenance/verify-backup.cjs \
  --from "$BEFORE" --restore-copy --to "$REHEARSAL"
```

所有备份/恢复目的地必须全新、私有，不能位于uploads/feedback内部。必须使用SQLite backup API或等价一致性备份，不能只复制仍在写入的`.db`而遗漏WAL。

已有反馈和申请附件的服务器必须传`--feedback`，两者共用FEEDBACK_UPLOAD_PATH。只有确认没有任何此类附件且目录确实不存在时才可省略该参数；不能新建空目录假装原附件齐全。

verify会检查备份清单、文件哈希、SQLite完整性/外键，不检查“数据库每条引用的文件都存在”。已缺失引用需单列；必要时用原课时只读inspect和人工抽查查明，不以空文件补齐。配置另行备份。

恢复工具只生成隔离副本，不切换正式服务；会调整常见file_path/video_path，因此恢复副本的绝对路径变化是预期差异。后续旧列对比的基线应在恢复副本上重新生成，不能拿包含原绝对路径的before哈希直接当恢复副本基线。

## C. 在副本演练结构迁移

```bash
node "$KIT/scripts/preflight.cjs" --app-root "$APP" \
  --db "$REHEARSAL/database.db" --output "$REPORTS/rehearsal-before.json"
node scripts/lesson-maintenance/schema.cjs --db "$REHEARSAL/database.db" --dry-run
node scripts/lesson-maintenance/schema.cjs \
  --db "$REHEARSAL/database.db" \
  --uploads "$REHEARSAL/uploads" --feedback "$REHEARSAL/feedback" \
  --backup-dir "$REHEARSAL_BACKUP" --apply --maintenance-confirmed
node "$KIT/scripts/preflight.cjs" --app-root "$APP" \
  --db "$REHEARSAL/database.db" --compare "$REPORTS/rehearsal-before.json" \
  --output "$REPORTS/rehearsal-after.json"
node scripts/lesson-maintenance/schema.cjs --db "$REHEARSAL/database.db" --dry-run
```

1031正常库预期pending为1032/1033/1034；1032或1033库只补剩余；1034正确库应无新迁移。更早库会有其他前置。dry-run只列尚未登记的文件，不执行SQL、不校验业务保持；其旧codeReference提示写1031，不表示实际只能执行1031，版本以完整version/name和审核提交为准。apply会运行完整迁移器，不限本包三份SQL。

确认结构完整性/FK、原列/行、人工教材、课程图片、报名、teacher旧范围、余额/订单、附件及新授权流程。重复迁移无新增pending，不复活撤销授权。若启动副本做应用冒烟，必须显式设置副本DB_PATH、UPLOAD_PATH、FEEDBACK_UPLOAD_PATH及私有测试端口，确认不接正式外部服务/AI；不能读默认配置误连正式库。

## D. 维护窗口迁移目标库并发布

仅副本演练通过且真实服务仍停写时执行：

```bash
node scripts/lesson-maintenance/schema.cjs --db "$DB" --dry-run
node scripts/lesson-maintenance/schema.cjs \
  --db "$DB" --uploads "$UPLOADS" --feedback "$FEEDBACK" \
  --backup-dir "$APPLY_BACKUP" --apply --maintenance-confirmed
node scripts/lesson-maintenance/verify-backup.cjs --from "$APPLY_BACKUP"
node "$KIT/scripts/preflight.cjs" --app-root "$APP" --db "$DB" \
  --compare "$REPORTS/before.json" --output "$REPORTS/after.json"
node scripts/lesson-maintenance/schema.cjs --db "$DB" --dry-run
```

新后端`config/database.js`加载就自动迁移并做其他旧结构兼容，故不能先启动再备份。显式迁移和复核后，再按原运维方式启动同一审核提交的后端、发布前端完整构建和主题资源；不要沿用Windows本机端口配置。最低就绪schema为1034，health必须ready。

启动前后仍要人工抽查账号/教材/文件和原余额/订单，以及学生学习、导师范围、teacher观察、反馈转交/回复、通知和正常兑换。新建/恢复观察严格校验，撤销旧授权可不依赖有效报名；先清理职责再教师迁校。按《数据与人工配置清单.md》逐课配置学校，不导入测试内容。确认后才退出维护。

## E. 失败停止及回退

- 任意命令非零、迁移身份冲突、完整性/FK错误、旧数据变动或附件不符：停止发布，保留日志/当前快照，核对已验证联合备份，不手工改迁移编号或清库。
- 升级事务中断应整体回滚，重新预检实际状态再判断，不能盲目重放单份SQL。
- 未产生新业务写入时，可停写后从联合备份恢复到全新目录并配套旧代码，再验证后人工切换。
- 已产生新教材/消息/金币/订单时，先保存升级后快照和附件，再制定差异恢复方案，不能直接恢复旧库丢新交易。没有破坏式down迁移。
- 恢复工具尚未重定位1034暂存课程包的staging_dir。含暂存记录的1034库异地恢复后，旧到期记录的路径校验可能阻塞所有新课程包上传，不能仅让用户重传就当作修复。必须先受控重定位并核对实际文件，或另行批准暂存处置方案并验证，再启用课程包上传；保留成功导入历史与正式课程。本包不提供该适配。迁移前1031备份没有这些记录，不受此项影响。

本轮不启用AI，不换密钥，不自动部署自定义代码。新版本正式上线日期、维护窗口、备份保管与回退负责人由维护方确认。
