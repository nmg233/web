# 版本目录发布与恢复

适用本轮整改代码，需先合并并提交到实际发布分支。用户已确认采用新布局；本文只准备操作步骤，不代表服务器已经迁移或通过验收。

## 1. 布局与一次性迁移

```text
/opt/pbl-platform/repo/                  获取 Git 代码，不承载新的构建发布
/opt/pbl-platform/releases/<SHA>-<时间>/  前后端属于同一发行版
/opt/pbl-platform/current -> 发行版目录  systemd 和 Nginx 共用
/etc/pbl-platform/backend.env            外置配置
/var/lib/pbl-platform/pbl_platform.db    持久数据库
/var/lib/pbl-platform/uploads/           公开业务上传
/var/lib/pbl-platform/private_uploads/   私有反馈附件
/var/lib/pbl-platform/backups/           数据库和两类附件备份
```

先在维护窗口备份现有数据库、公开上传、私有上传和 systemd/Nginx 配置。确认现有 `backend/private_uploads` 软链接的目标仍是 `/var/lib/pbl-platform/private_uploads`，不要删除链接目标，不要将数据库搬入发行目录。

在环境文件确认以下路径（保留原有 JWT_SECRET、PORT、CORS 等其他配置，不覆盖整个文件）：

```dotenv
DB_PATH=/var/lib/pbl-platform/pbl_platform.db
UPLOAD_PATH=/var/lib/pbl-platform/uploads
FEEDBACK_UPLOAD_PATH=/var/lib/pbl-platform/private_uploads
HOST=127.0.0.1
NODE_ENV=production
```

数据库及上传目录必须存在，服务用户 `deploy` 必须能读写；缺失时先查明原因，不能用空数据库替换。首次切换前，旧仓库必须已有可运行的 backend 和 frontend/dist；若 `/opt/pbl-platform/current` 尚不存在，可让它先指向现有仓库：

```bash
test ! -e /opt/pbl-platform/current && test ! -L /opt/pbl-platform/current
ln -s /opt/pbl-platform/repo /opt/pbl-platform/current
```

若 current 已存在，先检查 `ls -ld` 和 `readlink -f`，不要直接覆盖。

systemd 保留原 User/Group，并通过 `sudo systemctl edit pbl-backend` 设置：

```ini
[Service]
WorkingDirectory=/opt/pbl-platform/current/backend
EnvironmentFile=/etc/pbl-platform/backend.env
ExecStart=
ExecStart=/usr/bin/node app.js
```

在实际 Nginx 站点配置中将静态 root 改为 `/opt/pbl-platform/current/frontend/dist`。保留 `/api` 反代，保持私有目录不可公开访问；签名视频流需保留 Range 请求。视频最大 500 MB，Nginx 的 `client_max_body_size` 须高于这一限制并容纳 multipart 开销，例如 `510m`；上传超时可按网络情况设置 `client_body_timeout 1800s`、`proxy_read_timeout 1800s`。这些不是全站默认值建议，优先限制在上传接口相关 location。

```bash
sudo systemctl daemon-reload
sudo nginx -t
# 仅两项检查均成功后执行
sudo systemctl restart pbl-backend
sudo systemctl reload nginx
sudo systemctl show pbl-backend --property=WorkingDirectory --value
curl -fsS http://127.0.0.1:3000/api/health
```

对照实际 PORT 修改健康检查地址。完成此步骤后再使用新脚本；新布局不要继续运行原地更新的 deploy.sh。初次布局迁移本身不由发布脚本自动执行。

## 2. 正常发布

前置条件：Node/npm 可用、Python ≥3.9（优先明确指定已安装的 Python 3.11）、本地 C/C++ 编译工具、Git、tar、curl、sqlite3、flock、systemd；发布账号需具备指定服务的启停权限。不要为了部署盲目升级系统全局 npm 或替换系统 Python。

```bash
cd /opt/pbl-platform/repo
PYTHON=/usr/bin/python3.11 bash scripts/deploy-release.sh main
```

`main` 是示例发布分支，发布 xzx-2 时明确传入 `xzx-2`。脚本 fetch 指定分支、按 commit SHA 导出干净代码，不切换仓库分支、不带入未提交文件。只允许一个部署同时运行。

执行顺序：

1. 核对 current、systemd 工作目录、外置路径和 Python；在新 staging 目录安装依赖、编译原生 SQLite 并执行连接冒烟测试。
2. 前端 lint、测试、构建；在数据库一致性副本执行迁移、integrity_check、foreign_key_check，线上数据库此时不变。
3. 将 staging 保留为独立版本目录，停止后端，在一致维护窗口备份真实数据库和两类附件。
4. 用同目录临时软链接及 `mv -Tf` 原子替换 current，启动服务；检查健康响应中的实际 SHA、数据库就绪和 schema_version ≥19。
5. 健康失败恢复旧 current 并重启旧服务；成功后清理队列失败会明确告警，不假装处理成功。

发行根目录、配置、服务名和健康地址可通过环境变量指定。`DATA_ROOT` 默认 `/var/lib/pbl-platform`，生产保持此默认；临时演练可指定独立测试根。数据路径会解析真实目标后检查范围，禁止逃逸。脚本不会自动删除旧版本或失败的 staging。

注意：单个 current 切换保证前后端从同一目录发布，但无法使已打开的浏览器瞬间丢弃旧页面。发布后要验证旧页面刷新、API 兼容、懒加载资源失败提示；需要短维护窗口控制切换期间的新请求。

## 3. 数据迁移边界

018 增加课时快照、学生绑定、历史报告绑定、逐题反馈、定向修复审计和结课记录；019 增加学校状态、通知 outbox、重试幂等记录和整班迁移审计。都是新增表/列，不删已有答案、分数或报告。迁移按版本登记，同一版本不会重复执行。本轮018/019尚未发布，只应用到隔离库；若部署库已应用其他来源的同编号迁移，先核对SQL和实际表结构，不得仅凭版本号跳过差异。

历史内容无法可靠复原时使用可取得内容建立兼容快照，页面明确提示。管理员只能为尚未结课的指定学生补齐缺失卡片/题目/视频；已有题目和作答不替换，机会不重置。历史报告仍引用提交时对应的兼容版本。

**代码回滚不等于数据回滚。** 自动回滚只恢复链接，不会自动覆盖数据库和附件，避免抹掉新版本已经接受的用户写入。即使结构为增量，旧代码也可能不理解新的业务语义：旧版对内容版本和结课的保护不完整，回滚后应立即限制教学编辑/学生写入，评估后再恢复服务，不能把旧版重新开放当作无风险降级。

## 4. 备份与恢复演练

```bash
cd /opt/pbl-platform/current
ENV_FILE=/etc/pbl-platform/backend.env bash scripts/backup-db.sh
ENV_FILE=/etc/pbl-platform/backend.env bash scripts/backup-uploads.sh
sudo BACKUP_APP_DIR=/opt/pbl-platform/current bash scripts/install-cron.sh
```

定时任务使用 current 的逻辑路径，不固定到已淘汰版本。默认保留每种最近七份，生产还需异地备份、磁盘容量和告警，七份本机副本不是灾备保证。

附件脚本分别生成 `uploads-<时间>.tar.gz` 和 `feedback-uploads-<时间>.tar.gz`，归档内路径相对于各自上传根。目标目录任一缺失都会失败。恢复时两种压缩包必须分别还原，不能合并到公开目录。不要公开备份目录。

首次发布前，在新的隔离目录演练，不直接覆盖线上数据：

- 复制指定数据库备份到隔离 DB_PATH，检查 integrity_check/foreign_key_check，再启动隔离后端。
- `tar -tzf` 检查两类归档的路径与文件，再分别解压到隔离 uploads/private_uploads，核对文件数量和关键附件哈希。
- 使用隔离账号验证学习报告、旧作答、资料下载及私有附件鉴权；测试发布构建失败、切换后健康失败和旧版重启失败。
- 正式恢复需要先停服、保存故障时现场副本，明确选定的三个备份和可接受的数据损失窗口，再执行恢复。不得自动恢复数据库却保留另一时间点附件，也不得对生产目录递归清空。

本轮 Windows 自动测试只能证明代码和脚本模拟边界，不能替代阿里云 Linux 上的 systemd/Nginx、glibc/native binding、长视频/弱网与完整恢复演练。所有结果必须记录发行 SHA、环境和日期。
